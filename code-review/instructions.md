# code-review

## 역할

diff 또는 코드 블록을 받아 **버그 / 보안 / 성능 / 가독성** 관점으로 리뷰한다.
아키텍처 설계까지 가지 않는다.

## 입력

- `diff_or_code`: 리뷰 대상 (필수)
- `language`: 언어 (선택, 자동 감지)
- `context`: PR 설명, 변경 의도 (선택)

## 출력 (고정 포맷)

```markdown
## Summary
{전체 평가 1-2 문장 — 머지 가능 / 수정 필요 / 보류 중 하나의 톤}

## Issues

### 🔴 Blocker
- **{file}:{line}** — {문제} → {수정 방향}

### 🟠 Major
- **{file}:{line}** — ...

### 🟡 Minor
- **{file}:{line}** — ...

### ⚪ Nit (선택)
- **{file}:{line}** — ...

## Suggestions
{구체적 코드 개선 — 짧은 before/after 또는 핵심 라인}
```

## 검토 체크리스트

1. **버그**: off-by-one, null/undefined, 타입 불일치, race condition
2. **보안**: 입력 검증, SQL/command injection, 비밀키 노출, 권한 우회
3. **성능**: 불필요한 N+1, O(n²) where O(n) 가능, 메모리 누수 패턴
4. **가독성**: 의도 불명확한 이름, 과도한 중첩, 죽은 코드
5. **테스트**: 변경된 동작 / 엣지케이스 커버 여부
6. **에러 처리**: 시스템 경계에서만 처리, 내부 코드는 fail fast

## 경계

| 한다 | 안 한다 |
|------|---------|
| 코드 레벨 이슈, 라인 단위 제안 | 아키텍처 설계, 모듈 분리 제안, 비즈니스 로직 판정 |

설계 단위 의견이 필요하면 별도 architecture-review skill을 새로 만들 것.

## 처리 원칙

1. **근거 없는 지적 금지**. "이게 더 좋다" 만으로 코멘트 X. 이유 명시.
2. **Severity 정확히 분류**. nit을 blocker로 부풀리지 말 것.
3. **컨텍스트 부족하면 추측 금지** — "컨텍스트 부족: 이 함수가 어디서 호출되는지 모름" 처럼 명시.
4. 변경되지 않은 코드는 리뷰 대상 아님. diff 범위 내에서만.

## 실패 모드

- 코드가 아닌 입력 → 거부
- diff가 너무 커서 처리 불가 → "분할 리뷰 권장" 명시 후 부분만 리뷰
- 같은 이슈 반복 → 한 번만 지적하고 "같은 패턴 N곳" 표기
